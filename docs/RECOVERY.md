Итого по коду: **один JSON + 11 SQLite-баз приложения + отдельная SQLite session + конфигурация/ключ шифрования**. Дополнительно могут существовать SQLite `-wal`, `-shm`, `-journal`: сырое копирование только основного файла живой базы ненадёжно. Использовать согласованный SQLite snapshot либо подтверждённую остановку всех писателей; не удалять sidecar-файлы живого процесса.

`data/state.json.lock`, профильные/account lock-файлы и незавершённые `state-*.tmp` не заменяют основное состояние. Не «лечить» блокировку удалением файлов при работающих процессах. Неизвестные старые файлы сначала инвентаризировать, не удалять автоматически.

Для полноценного восстановления вне этого набора нужны: точная версия кода и схем, манифест файлов, фактически установленные Python/SDK/зависимости, systemd units и enablement, пользователь/права файлов, Nginx и TLS-сертификаты, DNS/firewall/Oracle-сетевые правила, расписание backup и место хранения копий. Runtime-архив ниже не содержит всю конфигурацию хоста. Сведения о новых локальных dependency locks — в [DEPENDENCIES.md](DEPENDENCIES.md); они не удостоверяют фактическую среду production.

## Что действительно делает текущий backup

`scripts/backup_runtime.py:21–60` создаёт `APP/backups/runtime-<UTC>-<UUID>.tar.gz`. Он получает отдельный SQLite snapshot каждой `data/*.sqlite3` и `desktop/bot.session` через SQLite backup API, проверяет `integrity_check`, добавляет `data/state.json` и `.env`, затем атомарно переименовывает временный архив. Права ограничены владельцем; старые архивы не удаляются, retention/offsite-проверка не реализованы.

**`.tar.gz` — сжатие, а не шифрование.** Описания systemd «encrypted state backup» вводят в заблуждение: в архив помещаются `.env` с master key, session и зашифрованные поля state вместе. Доступ к архиву нужно считать доступом к секретам. Не отправлять его в Git, публичные артефакты CI или чат; права `0600` не заменяют шифрование резервных копий.

Каждая SQLite-копия внутренне согласована, а JSON записывается атомарно, но **общей транзакции между всеми базами и JSON нет**. Наличие execution journal помогает разбирать границу операций, однако не доказывает автоматическую корректность восстановления; P1-01/P1-05/P1-07 остаются открытыми. Успешный `integrity_check` не доказывает верное происхождение позиции.

## План будущего восстановления — только после отдельного разрешения

1. **Зафиксировать границы.** Определить точные APP/backup-пути, сеть, версию кода, все процессы-писатели и время копии. Не начинать с очистки сервера. Согласовать обслуживание; остановка копирования сама по себе не означает закрытие всех позиций.
2. **Сохранить текущее состояние до изменений.** При разрешённом обслуживании остановить/приостановить всех писателей: bot, web, observers и backup jobs. Получить согласованный набор из таблицы, сохранить контрольные суммы и права без вывода секретов. Не смешивать JSON одного момента с базами другого.
3. **Отделить code rollback от data rollback.** При откате кода оставить новейшие совместимые execution records. **Нельзя восстанавливать старые JSON/SQLite поверх состояния после совершённых сделок:** это стирает известные исполнения, `cloid`/operation ID и может вызвать повторный ордер. Без совместимости схем старый код не запускать.
4. **Проверять копию изолированно.** Новый каталог/среда, без запуска бота, рабочего Telegram session, финансируемого signing key и без доступа к реальным торговым действиям. Сначала проверить состав, строгую структуру/конечность чисел JSON, целостность каждой SQLite, версии схем и соответствие master key; проверки не должны печатать секреты. Эти действия в фазе 0 не выполнялись.
5. **Сверить ownership с биржей.** После отдельного разрешения на чтение сопоставить свежие позиции, открытые ордера и исполнения с `cloid`/order ID, execution journal, AI proposals и источниками. Совпадение монеты или размера недостаточно. `UNKNOWN`, `SUBMITTING`, `PREPARED` и recovery/HOLD-метки не снимать без доказательств. Не объявлять чужую/ручную позицию ботской по старому hardcoded recovery-скрипту.
6. **Проверить конфигурацию запуска.** Точный network, profile flags, ключи, доступы, службы и версия SDK. `AUTO_TRADING=false` не блокирует все ручные/AI endpoints; для restore drill нужна реальная изоляция, а не только этот флаг. Не запускать рядом две копии production watcher на один аккаунт.
7. **Разрешать торговлю отдельным решением.** После сверки и проверки ограничений запустить по согласованному порядку, наблюдать реальные циклы каждого процесса и отсутствие неопределённых операций. `/health` подтверждает ответ web-процесса, а не работоспособность бота, биржи или торговой сверки. Наличие restart policy тоже не доказывает их корректность.

Критерий полного restore drill: отдельный отчёт с версией/манифестом копии, средой, проверками всех перечисленных хранилищ, согласованием ownership и доказательством отсутствия реальных действий в тесте. **Восстановление указанного рабочего набора/production в фазе 0 не заявляется проверенным.** Синтетические `tests/test_backup_runtime.py` проверяют, например, состав архива, отдельные SQLite/WAL-данные, целостность и отсутствие удаления предыдущих копий; это полезный более узкий результат. Актуальные результаты/дополнительные синтетические проверки описываются отдельно в [PHASE0.md](PHASE0.md), не подменяя production restore.

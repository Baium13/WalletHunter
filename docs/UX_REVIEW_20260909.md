# Проверка экранов Wallet Hunter — 9 сентября 2026

Проверены текущие компоненты и их рендер в изолированном браузере на тестовых данных. Примеры балансов/сделок в скриншотах — фикстуры, не результаты production. Реальные торговые кнопки на сервере не нажимались.

| Экран / окно | Вывод и минимальное упрощение |
|---|---|
| Главная | Длинная лента: график, статистика, AI Core, консенсус, Manual Copy, события. Оставить сверху капитал, позиции и последний результат; большой Core открывать по желанию. |
| Позиции | Основная информация полезна. Пустые категории источников лучше скрывать; на мобильном их ряд сейчас прокручивается горизонтально. |
| Деталь позиции | График и хронология нужны. Полную матрицу семи агентов можно свернуть; показывать итог и причину сделки первыми. |
| Manual Copy | Исправлено: добавление — только сохранение; START отдельный, анализ только по нажатию. Свежая проверка при START обязательна. Капитальную базу лидера и техническую историю можно держать свёрнутыми. |
| Подтверждение START / паузы | Сохранить сеть, долю и предупреждение о реальных операциях. Ошибка теперь внутри окна, кнопка восстанавливается после подтверждённого отказа. При потере ответа — только проверка сохранённого состояния, не автоматический повтор. |
| Анализ ручного лидера | Запрос только по отдельной кнопке. Неполная история не должна блокировать само добавление адреса. |
| Лидеры | Нужны рейтинг и краткая сводка поиска. Длинный перечень технических состояний и покрытие истории — в деталях. Режим просмотра здесь стоит обозначать явно: он не меняет публичный поиск. |
| Деталь лидера | Основные метрики полезны. Компоненты оценки и сырые поля поведения (`value`, `reason`) лучше убрать в подробности; показывать понятную причину отсутствия метрики. |
| Агенты | Core и краткие карточки работают. Повторяющийся большой консенсус/описания можно сократить. Изменение вкладки PAPER/LIVE не должно выглядеть как переключение аналитического worker. |
| Деталь агента | Сырые `heartbeat`, `missing_inputs`, версии и коды причин мешают чтению. Первым экраном — состояние, инструмент, вывод и возраст данных; технические поля — раскрываемые. |
| Аналитика | Оставить график и основные финансовые показатели. Служебные пояснения о калибровке — в разделе «Подробнее»; режимы результатов не объединять. |
| События | Категории и раскрываемые технические данные уже уместны. Не переносить внутреннюю ленту обратно в Telegram. |
| Система | Верхний большой блок API можно свернуть: сначала состояние системы и конкретная проблема, затем подробные лимиты. Ничего не перекрашивать в HEALTHY без доказательств. |
| Настройки | Язык/приватность повторяют шапку — оставить один основной доступ либо считать второй быстрым. Раздел режимов должен явно называться «Отображение», если не меняет исполнение. |
| LIVE_CONFIRM | Сеть, объём, цена, срок действия и явное подтверждение обязательны. Технические поля slippage можно перевести в короткую подпись, но не скрывать торговый риск. |

Предложения вне Manual Copy не применялись: это обзор для выбора следующего компактного UX-прохода, а не новый редизайн.

## API

По [официальной документации Hyperliquid](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/rate-limits-and-user-limits) REST ограничен 1200 единицами **веса** в минуту на IP, не 1200 произвольными запросами. Часть чтений стоит 2, остальные обычно 20, `userRole` — 60; большие ответы истории стоят дополнительно. Публичного переключателя увеличения квоты эта документация не предоставляет. Лимиты торговых действий по обороту — отдельная категория, они не увеличивают информационную REST-квоту.

Практический путь ускорения: общие рыночные подписки, кеширование безопасных справочных данных, история по запросу и инкрементально, приоритет интерактивных свежих проверок, низкоприоритетный Discovery при нагрузке. Резерв для reconciliation/открытых позиций сохраняется. Увеличивать локальный лимит выше биржевого или обходить ограничения сменой IP не требуется.
